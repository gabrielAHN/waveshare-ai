# Security model

Setup belongs to the [device](../devices/waveshare-esp32-s3-touch-amoled-1-8-v2/README.md#install), [Hermes](../plugins/hermes/SETUP.md) and
[Home Assistant](../plugins/home_assistant/SETUP.md) guides. This document describes the trust
boundaries of the ESP-IDF core, bridge, dashboard capabilities and stock SDK voice path.

## Assets and storage

| Secret / state | Location |
|---|---|
| Wi-Fi passwords | private `.env` (0600), then board NVS over USB; never compiled into firmware |
| Board identity (32 bytes) | generated by the board, NVS `home_wifi/device_id`; bridge stores only SHA-256 |
| Bridge TLS private key | bridge config `tls.key` (0600); the board holds only its certificate pin |
| Hermes machine-client secret | `authelia-client.json` (0600), for dashboard usage and capabilities |
| Sensor machine-client secret | `home-client.json` (0600), for the protected sensor endpoint |
| Session pseudonym HMAC key | bridge `board.key` (0600); never sent to the board |
| Home Assistant token | endpoint host behind the auth proxy; neither bridge nor board receives it |
| Machine OAuth tokens | bridge memory, short-lived and re-minted without refresh tokens |
| Phone OAuth tokens | bridge memory during approval, discarded after userinfo |
| Phone user/group snapshot | bridge `boards.json` (0600); not an OAuth credential |
| SDK identity/key and approval | derived on the board; SDK device/pairing storage in the bot profile |
| Front-owned approvals | private `gadget-grants.json` ledger and profile pairing files |

The config directory is **0700**. Secrets do not belong in arguments, logs, plugin settings or this
repository. Reflashing preserves NVS; it is not a credential wipe.

## Trust decisions

### Board and bridge

The board pins **SHA-256 of the bridge TLS leaf certificate DER**, obtained through discovery or
an explicit USB candidate. `pair_tls.c` uses the pin as its trust anchor, rather than CA/hostname
validation. Discovery is not proof of ownership: the operator compares the six-digit code on
both screens and approves only a match. Only the host can confirm enrollment.

The code binds the certificate fingerprint and SHA-256 of the board identity with the domain
label `waveshare-ai-enroll-v1` plus its NUL byte. A mismatched responder produces a different code.
Denial, expiry or cancellation after sending the identity rotates it. One enrollment may be
pending at a time; pending requests expire after 120 s and the endpoint limits an IP to 60
requests/minute. The operator-opened window defaults to 180 s.

After enrollment the bridge authenticates the board by its bearer identity hash in `boards.json`.
The bearer travels only inside pinned TLS. `allow_ip` can further restrict LAN peers; the HTTPS
API and gadget front bind the configured RFC1918 address.

### Phone authorization and shared groups

A person approves the board through the provider's OAuth device grant, public client, portal
login/2FA and explicit consent. The verification URL must use HTTPS on that provider's host.
The bridge reads userinfo, saves user/name/time/groups, then discards access and ID tokens.
Phone requests require an explicit `X-Provider` identifying a served provider.

Providers resolving to the same gateway share one flow, QR and sign-out. **Each still checks its
own group allowlist**: Hermes authorization does not itself permit Sensor data. Membership is a
snapshot at approval time, not continuous IdP polling; changed groups require a new sign-in.
The board receives a public code, URL, display name and bounded state, not gateway credentials.

### Dashboard metadata and sensor endpoint

The dashboard plugin exposes exactly **`/usage`** and **`/bots`**. Its token provider pins RS256,
issuer, audience, client id, expiry/issued-at and the scope for the exact route. A JWT valid for
usage does not authorize bot capabilities or dashboard administration. JWKS failure closes the
route. The bridge's separate scopes are `hermes.sessions.read` and `hermes.helper.command`.
The plugin reads session metadata, not message contents.

Sensor uses a separate client-credentials bearer accepted by the auth proxy **only for its exact
resource path**. Configure the client-specific allow rule before an explicit deny rule and use a
bearer-only authz endpoint, without cookie login redirects. That client cannot request `hermes.*`
scopes. The service's Home Assistant credential stays behind the proxy. The bridge returns Sensor
readings only for a board authorized by Home Assistant's phone/group policy.

### Ask: stock SDK in profile gateways

The board connects to **`wss://<bridge>:8768/gadget/<bot>`**, pinned to the enrolled certificate.
The front checks enrollment, the bridge's Hermes phone authorization and its configured profile
map. It records the board's SDK approval in that profile's pairing store, removes the board
Authorization header from the upstream upgrade, then carries the SDK protocol to the profile's
**loopback-only** stock `gadget` platform. Set host/port before enabling it and check the listeners.

SDK challenge/auth uses a separate key derived with HMAC-SHA256 and the domain label
`waveshare-ai-gadget-key-v1`. The front owns enrollment/phone approval; it does not inspect audio,
agent replies or quota. The board's `/v1/bots` gate blocks recording on explicit quota exhaustion.
Profile turns retain that profile's model, tools and security policy. Approval prompts are declined
by the board. Stop requests cancellation; cancellation cannot undo already-completed side effects.

The front's 5 s sweep removes its grants for removed/signed-out boards. The stock adapter reports
`unpaired`; independently created approvals are outside the front's ledger. Profile SDK storage
and grant files are private. [Voice contract](../plugins/hermes/GADGET-SDK.md).

## Threats and limits

| Threat | Control / limit |
|---|---|
| Rogue discovery / interception | certificate pin and comparison code; never approve a mismatch |
| Unknown LAN client | enrollment window/operator confirmation; enrolled bearer checks afterwards |
| Lost board | `waveshare-bridge boards --remove <id>` revokes it; `--revoke-phone <id>` clears phone approvals |
| Credential disclosure | hidden input, private files, bounded logs and publication checks |
| Extracted firmware | no Wi-Fi or service credentials in the image |
| Physical flash access | NVS is **unencrypted**; a person with the board can read Wi-Fi and identity |
| Stale quota / group evidence | known exhaustion persists until fresh recovery; group policy changes require new approval |
| Voice retry / cancellation | connection failure is visible; utterances are not blindly replayed; side effects may already exist |

USB setup and test hooks require physical access. CRC checks catch corruption, not hostile local
operators. Hooks cannot confirm enrollment; test injection is logged as such and is not physical
touch/microphone evidence. Host renders likewise do not establish board behavior.

## Physical security and publication

NVS forget is logical deletion; flash pages can retain remnants. Deliberate decommissioning can
use `idf.py erase-flash` from the named device's `firmware/` directory with the intended board attached. This erases
Wi-Fi and identity and requires fresh provisioning/enrollment. Do not erase during routine updates.

NVS/flash encryption and secure boot require deliberate ESP32-S3 provisioning. **eFuse writes are
irreversible**; this repository does not enable them automatically.

Keep `.env`, bridge/client files, profile SDK storage and infrastructure configuration outside git.
Run `tools/check-no-secrets.sh` for tracked content and `--history` for publication history;
`WAVESHARE_AI_DENYLIST=<private file>` adds your own domain, host and username terms. Suppress hit
output when it can disclose private values. Review the staged paths as well as scanner results.

# Hermes setup

This guide installs Hermes without Home Assistant. If both plugins use the same OIDC issuer,
public client, RFC 8628 endpoints and Host header, one phone approval and sign-out covers both.
Permissions do not merge: Hermes checks `providers.hermes.sign_in.groups`, while Home Assistant
checks its own groups.

Commands run from the repository root on the Hermes host. First complete the
[base-device setup](../../devices/waveshare-esp32-s3-touch-amoled-1-8-v2/README.md#install).

## Requirements

- Python 3.11+, git and `openssl` on macOS or Linux.
- Hermes, its dashboard at a loopback URL, and one to three configured profiles.
- An OIDC provider supporting client credentials, RFC 8628 device authorization, explicit consent,
  and `groups` plus a display name from userinfo. The example was tested with exactly Authelia 4.39.28.
- A reachable LAN address for bridge HTTPS port 8098 and gadget-front port 8768. Discovery uses
  `_waveshare-ai._tcp` (`_waveshare-ai._tcp.local.` in Python).

All hostnames are placeholders. Keep generated secrets and local configuration outside git.

## 1. Register the OIDC clients

Merge the following entries into your Authelia configuration. The machine client and public phone
client serve different trust boundaries and must remain separate.

### Machine client for dashboard metadata

The bridge requests `hermes.sessions.read` for `/usage` and `hermes.helper.command` for `/bots`.
The dashboard plugin verifies an RS256 JWT's issuer, audience, client id, times and exact-path scope.

```yaml
identity_providers:
  oidc:
    lifespans:
      custom:
        waveshare_bridge: {access_token: '1h'}
    clients:
      - client_id: waveshare-bridge
        client_name: Waveshare AI bridge
        client_secret: '$pbkdf2-sha512$...' # hash generated by Authelia
        public: false
        authorization_policy: one_factor
        lifespan: waveshare_bridge
        grant_types: [client_credentials]
        response_types: []
        scopes: [hermes.sessions.read, hermes.helper.command]
        audience: ['https://hermes.example.com/api/plugins/waveshare-sessions']
        access_token_signed_response_alg: RS256
        token_endpoint_auth_method: client_secret_basic
```

Keep the generated plaintext secret for the bridge's private JSON file. Only the hash belongs in
Authelia. These tokens cannot authorize chats, administration or Ask voice.

### Public client for phone approval

The public client has no secret. The policy below allows either example group to approve Hermes;
choose groups that match `bridge.json`.

```yaml
identity_providers:
  oidc:
    authorization_policies:
      waveshare_pairing:
        default_policy: deny
        rules:
          - {policy: two_factor, subject: 'group:admins'}
          - {policy: two_factor, subject: 'group:hermes_users'}
    lifespans:
      custom:
        waveshare_pairing: {access_token: 5m, id_token: 5m}
    clients:
      - client_id: waveshare-pairing
        client_name: Waveshare AI phone approval
        public: true
        authorization_policy: waveshare_pairing
        lifespan: waveshare_pairing
        consent_mode: explicit
        scopes: [openid, profile, groups]
        grant_types: ['urn:ietf:params:oauth:grant-type:device_code']
        response_types: []
        token_endpoint_auth_method: none
```

Userinfo must return `groups` and `preferred_username` or `name`. Validate the complete provider
configuration before restarting it. For another compatible provider, put its published issuer and
absolute device-authorization, token and userinfo paths in `bridge.json`. Configure the dashboard's
JWKS URL in its settings, or install with a parser-validated override:

```sh
waveshare-bridge plugin install --jwks-uri https://auth.example.com/keys
```

## 2. Install and initialize the bridge

```sh
python3 -m venv ~/.local/share/waveshare-bridge/venv
~/.local/share/waveshare-bridge/venv/bin/pip install -e ./bridge
export PATH="$HOME/.local/share/waveshare-bridge/venv/bin:$PATH"
waveshare-bridge init --launchd --label local.waveshare-bridge
```

On Linux, omit `--launchd` and run the service from a systemd user unit. `init` prompts for the
LAN bind address, port, loopback dashboard, token endpoint, machine client, scopes, audience,
bridge name and secret without echo. It creates `~/.config/waveshare-ai/` with mode 0700 and
private files with mode 0600. It refuses to overwrite an existing setup unless `--force` is given.

The Hermes portion of `bridge.json` is:

```json
{
  "providers": {
    "hermes": {
      "gateway": "http://127.0.0.1:9119",
      "client_file": "authelia-client.json",
      "sign_in": {
        "client_id": "waveshare-pairing",
        "groups": ["admins", "hermes_users"],
        "required": true
      },
      "tiles": ["sparkles", "ask"],
      "bots": ["helper", "atlas", "coding"]
    }
  }
}
```

Keep the top-level `bind`, `port`, `name`, `mdns` and `allow_ip` written by `init`. Profile ids are
examples matching the repository's scripted renders; replace them with up to three real Hermes
profile ids. `WAVESHARE_AI_CONFIG` or the global `--config-dir DIR` selects another directory.

Run in the foreground with `waveshare-bridge run`. For the generated macOS launchd job:

```sh
mkdir -p ~/Library/LaunchAgents
cp ~/.config/waveshare-ai/local.waveshare-bridge.plist ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.waveshare-bridge.plist
waveshare-bridge status
waveshare-bridge provider list
```

Use either launchd or the foreground service, never both.

## 3. Install the dashboard plugin

```sh
waveshare-bridge plugin install \
  --issuer https://auth.example.com \
  --jwks-uri https://auth.example.com/jwks.json
hermes plugins enable waveshare-sessions
```

The installer writes non-secret settings for only `/usage` and `/bots`. `--hermes-home DIR` selects
a Hermes home and `--source DIR` selects a plugin source directory. Restart the dashboard yourself
at a quiet time; restarting ends chats hosted by that process. See the
[dashboard plugin reference](dashboard-plugin/README.md).

## 4. Configure Ask voice

Create and configure the Hermes profiles first. Then print the pinned stock SDK changes:

```sh
waveshare-bridge hermes sdk-setup \
  --bot helper=8775 --bot atlas=8776 --bot coding=8777
```

After review, apply them:

```sh
waveshare-bridge hermes sdk-setup \
  --bot helper=8775 --bot atlas=8776 --bot coding=8777 --apply
```

The command installs the pinned external SDK in each profile and configures its listener at
`127.0.0.1:PORT/gadget` before enabling it. `--skip-install` configures an existing installation;
`--port N` changes the front port. Keep `providers.hermes.bots`, `gadget_sdk.profiles` and the
dashboard's `command_profiles` aligned. Restart each selected profile gateway and the bridge after
reviewing changes. No listener should bind the profile ports on every interface.

## 5. Enroll and approve the board

1. Run `waveshare-bridge enroll` on the host. `--seconds N` changes the 180-second window.
2. On the board, open **Settings > Hermes**, select the discovered bridge, and compare the six-digit
   code on both screens. Approve only an exact match.
3. Open **Phone sign-in**, scan the QR, complete 2FA and explicit consent, and confirm the account
   belongs to a configured Hermes group.

Discovery is not proof of ownership; code comparison establishes the enrollment. If mDNS is
blocked, an explicit pinned candidate can be sent over USB with a test address:

```sh
python tools/pair_usb.py bridge https://10.0.0.10:8098 FINGERPRINT
```

This still requires code comparison. `waveshare-bridge boards` lists enrollments;
`boards --remove ID` revokes a board and `boards --revoke-phone ID` clears all phone approvals.
Signing out from a shared account clears every provider on that gateway. Phone approval is durable
local state, not continuous userinfo polling; sign out and approve again after group changes.

## 6. Verify

- `waveshare-bridge status` and `provider list` show Hermes, the expected tiles and sign-in gateway.
- An open session creates a Sparkles glow; working state is brighter and increases busy density.
- Ask can switch profiles, record after the hold, show transcript/reply, stop work and start a new
  chat. This requires a real board check; host renders do not prove microphone or speaker behavior.
- Requests without a valid machine token, wrong scope, wrong audience/client, expired token or JWKS
  validation fail closed at the dashboard plugin.
- Signing out or removing the board closes provider and SDK access; group changes apply after reapproval.

## Quota and troubleshooting

The optional official Hermes `quota` plugin writes local telemetry. Tests and documentation checks
must not refresh provider quota or use a real profile. Verified exhaustion stays blocked until
fresh usable evidence arrives; missing telemetry is not itself exhaustion.

| Symptom | Check |
|---|---|
| Bridge not found | bridge running on the reachable LAN address, mDNS permitted, no client isolation |
| Phone portal unavailable | public client, RFC 8628 grant, endpoint paths, HTTPS verification host |
| Sign-in refused | account belongs to a Hermes group; approve again after group changes |
| Sparkles or profiles unavailable | dashboard plugin active, machine issuer/audience/scopes/JWKS and profile allowlist |
| Ask gateway offline | selected profile's loopback SDK listener and bridge configuration agree |
| No quota persists | wait for fresh usable official quota evidence; a countdown alone does not clear it |
